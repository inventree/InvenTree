# 仓序改造规划

日期：2026-09-07；实施状态更新：2026-10-11。目标仓库：[rongxinzy/cangxu](https://github.com/rongxinzy/cangxu)。状态：基础追溯模型/API 和可扩容虚构演示数据已在开发分支验证，生产试点仍待验收。

2026-10-09 更新：实际生产资料对应的范围、验收条件与当前交付顺序见[业务需求基线](REQUIREMENTS.zh-CN.md)。本文件保留早期技术规划；其中阶段顺序以需求基线第 8 节为准，优先完成质量返工、供应商维修、分批交付、导入及盘点闭环，再深化完整拓扑与智能体。

## 1. 产品目标与边界

服务智算服务器从物料收货、备料、单机装配、测试、交付到返修的追溯流程。能够回答：某件配件在哪里、装在哪台机器/哪个槽位、连接了哪个端点、采用哪版配置、通过哪些测试、由谁变更。

第一阶段以真实工厂的一种机型、一个仓区和一条装配流程试点。原版收货、领料、装配、盘点先配置试用；有明确缺口才改代码。完整财务、全厂排程和产线自动控制另行评估，不能以本项目已覆盖宣传。

本地开发分支已实现首批基础模型/API 和虚构数据命令；硬件规格草稿、协议分类、交换端口与多端线缆样例已在 pro6000D 的开发库验证。下列完整拓扑、完整领退料闭环、正式质量放行、专用交互页面、自动采集与智能体仍按阶段规划推进；分支测试不等同于工厂生产验收。

演示数据通过 `python manage.py seed_cangxu_demo --scale-factor N` 扩展（默认 `1`，范围 `1–100`）。系数会同比放大合成整机、开账库存和采购收货数量；使用更大的系数重跑会幂等补齐记录，不会删除已存在的演示数据。数据仅供开发/压测，不能当作企业实际库存、采购记录或工程兼容结论。

## 3. 架构决定

- InvenTree 保持库存事实、采购/销售、BOM、工单的唯一业务主记录。
- 新增行业模块优先采用插件/Django App，引用上游对象，不复制一套库存表。对插件模型权限、迁移和生命周期先做技术验证。
- 扩展只读接口和受控写入接口；安装、换件和接线的跨表操作需要同一事务或持久化的可恢复流程。
- 仓序配置版本记录对上游 BOM/库存的引用和当时快照，历史版本不因上游数据修改而漂移。
- 先以 PostgreSQL 验证行业模块；保留上游数据库可移植性，pgvector 单独作为可选知识索引，不能让基础仓管强依赖它。
- React 原版页面继续可用，逐步加入单机配置、拓扑、接线、质量放行和助手入口。
- Pi 作为独立 TypeScript 服务，通过服务端业务工具访问 Django。普通用户不获得 shell、任意 SQL 或管理员密钥。

详细实体、关系和约束见 [行业数据模型设计](DOMAIN-MODEL.zh-CN.md)。

## 4. 分阶段交付与验收

| 阶段 | 交付 | 验收条件 |
|---|---|---|
| P0 原版试用 | 版本锁定、中文、角色、仓区、实际 BOM、演示数据 | 一笔订单完成收货/领料/装配/测试/退料/盘点；列出配置可解决与需开发的差异；恢复备份成功 |
| P1 物料与单机模型 | 行业目录、参数、槽位/端口、装机位置、设备标识、版本化配置 | 两种不同拓扑的样例；同一 SN 不能装入两机、槽位冲突被拦截；GPU 型号可查到具体实物 |
| P2 拓扑与线缆 | PCIe/NVLink/网络拓扑、连接器、多端线缆、端点占用、兼容规则 | 端口误插、重复占用、breakout 映射错误被拦截；互联类型不混淆 |
| P3 质量与返修 | 测试计划、采集、换件、复测与交付快照 | 换件后相关测试失效并复测；交付可还原；失败/缺测不能放行；返修旧件去向明确 |
| P4 仓库协作 | 按 P0 缺口补充盘点会话、差异复核、领退料交接 | 差异有调查记录和责任人；审批前库存不被无依据改动；重复提交只记一次 |
| P5 智能体 | 实时查询、知识检索、缺料分析、操作草稿 | 权限不越界、答案附来源/时间、数值经业务计算、变更经授权与执行前复核 |
| P6 试点生产 | 内网发布、扫码/打印验证、运维、回滚与培训 | 实际操作员完成验收任务；关键异常、并发、恢复与升级演练通过 |

阶段按依赖推进，P4 可随试点提前；具体排期在 P0 后根据开发人数、硬件样例和接口数量估算，当前不作生产可用日期承诺。

## 5. 核心接口与页面规划

接口路径为拟定设计，不是现成 API：

- `GET /api/cangxu/units/{id}/configuration`：当前装机、端点与来源。
- `POST /api/cangxu/units/{id}/installations`：安装到槽位；复用库存安装逻辑。
- `POST /api/cangxu/units/{id}/replacements`：原件拆回、替换件装入、记录原因及复测要求。
- `POST /api/cangxu/connections`：接线与分支映射；校验端点占用和工程规则。
- `POST /api/cangxu/units/{id}/inspections`：导入硬件/固件/拓扑观测，生成差异，不能静默覆盖配置。
- `POST /api/cangxu/units/{id}/releases`：验证配置版本和质量条件，冻结交付快照。
- 所有写接口带请求幂等键、操作者和期望配置版本；冲突返回可处理的错误，禁止伪报成功。

页面：物料技术档案、单机配置/槽位、可切换协议的拓扑图、扫码接线与换件、测试与差异、交付/返修档案、助手侧栏。真实硬件扫码与打印验证必须覆盖已有设备型号。

## 6. 数据迁移与索引

- 导入先暂存和校验：料号别名、单位、制造商 SN 重复范围、无 SN 物料策略、批次与库位。
- 历史账标记为账面、待核实或实盘确认。不能仅因 Excel 导入成功就视为实物已确认。
- GPU/交换板等逐件追踪；低价值线材可按批次库存，安装后需要连接追溯的线束分配内部实例编号。
- 把兼容表、手册和 SOP 建成有来源、版本、权限的知识库；异步索引需支持更新、删除、重试和重建。
- SN/订单号/料号精确查询；向量检索用于语义资料。库存和正式兼容结论执行前回查业务记录。

## 7. 验证策略

每个阶段提交对应的模型/接口测试；按上游贡献规范运行必要检查，不绕过 hooks。

- 模型：唯一性、层级防环、端点类型、时间区间、版本不可变、拆机库存守恒。
- 并发：双人装同一配件、双人占同一槽位/端口、重复请求、超时重试、后台任务重启。
- 集成：BOM 变更、替代料、部分完工、缺测拦截、换件复测、发货后返修。
- 浏览器：收货/安装/接线/盘点关键流程，中文错误信息、权限、扫码焦点、打印和网络中断反馈。
- AI：固定业务问题集对照人工真值；越权检索、过期资料、注入文本、错误 SN、无证据回答、重复执行。
- 运维：空库安装、原版升级、迁移回滚或备份恢复、权限导出、操作日志追踪。

生产验收标准：库存/装机/接线关键约束零已知失败；所有阻断问题关闭；备份恢复演练通过。性能阈值在拿到物料规模和并发人数后固定，记录基线并比较。

## 8. Git、发布与上游同步

- `origin` 指向 `rongxinzy/cangxu`，`upstream` 指向 `inventree/InvenTree`；禁止把仓序定制误推上游。
- 当前文档初始化提交可直接进入 fork；后续实现采用短生命周期分支，遵守人工审阅规范。
- 保留上游 LICENSE 与版权，README.upstream.md 作为初始快照；仓序 README 不挂上游 CI 作为本项目已通过证明。
- 上游合并采用专门分支，核验模型/API/前端扩展兼容性及迁移。确认 fork 发布目标和密钥前，不启用自动发布到上游的镜像/软件包目的地。
- 首个仓序发布需补齐应用品牌、独立镜像地址、版本标记、变更记录和回滚说明，避免 fork 名称与实际产物混淆。
